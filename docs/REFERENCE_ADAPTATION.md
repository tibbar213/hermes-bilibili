# 请求保护、字幕与发送核验

参考 Alterssss/dsh-bili-whale 的请求调度、完整字幕、私信历史和发送核验设计，在现有 Python/SQLite 插件内实现；不依赖 DSH、不增加第二个人格或长期记忆。

## 统一请求保护

插件的 B站 HTTP 请求由 profile 共用持久化保护，后台、手动工具和 CLI 子进程使用同一个 SQLite 数据目录。不同 profile、浏览器和其他程序的流量不在本插件控制范围内。模型、搜索供应商等非 B站域名的请求不占该额度。

| settings.json 设置 | 默认值 |
|---|---:|
| BILI_REQUEST_GAP_MS | 1500 |
| BILI_READ_HOURLY | 0（不限） |
| BILI_READ_DAILY | 0（不限） |
| BILI_WRITE_HOURLY | 12 |
| BILI_WRITE_DAILY | 30 |
| BILI_WRITE_GAP_SECONDS | 120 |

单并发；小时额度采用滚动一小时，日额度按 profile 主机本地日期。请求间隔最低 600ms，写操作间隔最低 120 秒，读取上限设为 0 表示不限次数，仍保留请求计数；显式正数可开启读取上限。写上限和间隔的无效/非正设置回退默认。所有非 GET/HEAD/OPTIONS 的请求合计写额度，包括主动评论、回复、动态、私信、上传和账户操作；不是每种功能各有 30 次。现有业务日额度继续生效，取先达到的限制。多步上传/发帖分别满足写操作间隔；普通间隔不足时进入 SQLite FIFO 等待队列，不占用网络并发槽，读取仍可进行。单次排队最多 300 秒，超时、额度用完或风控暂停时明确记为未发送，不计入实际请求次数。排队时间不消耗动作执行的 45 秒超时；实际发送仍保留超时与未知结果保护。队列不存凭据和消息正文，不会在进程重启后自行补发。

实际发起的尝试计数，即使失败或结果未知也不退还请求名额。拦截在网络发送前的不计入。暂停、次数和写入指纹重启保留；相同文本/表单操作已受理或结果未知时防止重复发送。未知格式的 multipart 请求仍限速，其业务去重继续由原有动作队列负责。

HTTP 412/429 与业务码 -412/-352/-799/-509/-10403 触发 5、10、20、30 分钟递增暂停，之后最高 30 分钟；Retry-After 要求更久时遵守更久时间。暂停到期后，同一故障接口成功才清除连续风控级别，其他接口成功不算恢复证明。停止立即重新签名/重试 -352，不自动重试 B站写请求。

这些是本地请求策略，不是 B站官方承诺的安全阈值。状态查询的 traffic_now 提供请求计数和剩余额度；request_guard_now 保留评论回复专门的 120 秒/12 次/30 次配置及暂停状态。

## 完整字幕

优先签名的 player/wbi/v2，缺轨道时尝试 subtitle/web/view；优先中文轨道，最多尝试三个候选。完整保留授权下载 URL 并及时取回，不将 URL 或 Cookie 写入字幕记录。只访问受信任的 B站 HTTPS 字幕域名，不恢复抽帧或语音转写。

成功下载后，原始 JSON、时间戳文本和纯文本保存在 profile/bilibili/subtitles，文件权限 600。无 2000/1500 字截断：较长内容按每段 8000 字阅读并整合，任何分段失败都不能标为完整阅读；超过 24 万字本次停止分析，已下载原文仍保留。subtitle_evidence 给出轨道、cid、时间范围；subtitle_reading 表明整份已取得文本是否处理完成。字幕可能只覆盖当前分P及部分时间，不代表完整视频的全部画面或音频。旧摘要保留来源，不冒充本次按新链路重读；可明确要求重新看。

## 私信补读

首次启用仍跳过旧历史。后续从最新页向过去翻，按序号越过已处理边界，按消息 ID 去重并按时间/序号排序。分页失败、序号不前进或超过十页时保留游标；抓取完整后只推进到实际检查并持久化的消息，不跳到可能领先的远端 max_seqno。保持原有待处理队列、过期消息策略和重启续接。

## 评论核验

新发送的评论和回复保存独立接口回执与 rpid。可调用 bili_recall(memory_type="delivery", query="评论ID或回执ID")；query 为空检查最近一次。分别做登录态和匿名有限分页回读。接口受理、登录态可见、匿名回读可见是三个不同状态；一次没查到只记未确认，不判定删除、不自动重发。仅使用既有的主人读取权限，核验不会发布任何内容。旧记录没有确切评论 ID 时不补造。
